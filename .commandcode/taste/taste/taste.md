# Taste
- Delegates implementation decisions to the agent: when the agent has investigated an issue and judges a fix is feasible, the user wants it to go ahead and implement it rather than pausing for step-by-step approval. Confidence: 0.6
- Prefers root-cause fixes over workarounds: when a limitation traces back to a dependency (e.g. a library constant or a third-party binary), the user pushes to rebuild/patch that dependency from source rather than stop at a partial workaround. Confidence: 0.5
- Wants dependency/toolchain versions pinned: when a build relies on an external toolchain or unpinned third-party source, the user expects it locked to an exact version (and reproducibility verified) rather than left floating. Confidence: 0.65
- Wants "full honest comparisons" of competing solutions: when choosing between a new approach and the status quo, the user asks for a complete, balanced side-by-side that states costs, risks, licensing caveats, and what was not tested — not a one-sided pitch for the new option. Confidence: 0.75
- Expects the user-facing demo to be kept in sync with implementation changes: after a capability/build change lands, wants the demo page updated to reflect it rather than left stale. Confidence: 0.4
- Prefers a single canonical configuration over selectable variants: when one option is a degraded subset of another (e.g. a pruned toolchain), wants it removed entirely — including silent fallbacks to it — rather than kept as a toggle. Confidence: 0.5
- Wants externally-hosted resources (asset hosts/CDNs) overridable at runtime via a URL parameter or a global, with a documented precedence order, rather than by editing source. Confidence: 0.45
- Prefers consolidating onto one already-running server/process over adding a second one: when assets or services could be served by a separate server, wants them folded into the existing dev server on the same origin (relative URLs, no extra port or background process) instead. Confidence: 0.5
- Prefers running heavy compute off the main thread, in a Web Worker, to keep the UI responsive rather than blocking the page. Confidence: 0.55
- Wants new capabilities implemented consistently with how the existing LiveCodes product already does it, treating the current implementation as the reference to match. Confidence: 0.5
- Prefers defaults picked by empirical validation over caution: when a more capable option exists (e.g. a newer language standard), wants it tested against a matrix of cases and promoted to the default if it shows no regressions, rather than left conservatively one step behind. Confidence: 0.55
- Wants a concrete, runnable artifact (e.g. a self-contained HTML demo page) for evaluating a technical option, rather than a written assessment alone. Confidence: 0.5
- Wants analogous options kept in parity: when one variant/configuration is raised to a newer default (e.g. the C++ standard), expects the parallel setting for the other variant (e.g. C) to be raised to match rather than left divergent, and raises the question itself. Confidence: 0.4
- Prefers a lean user-facing UI without diagnostic/debug chrome: asks for informational badges about internal implementation details (e.g. which asset host is serving the toolchain) to be removed rather than surfaced to end users. Confidence: 0.4
- Wants one simple, uniform API surface shared across all language modes/variants, rather than per-language entry points: if there are three or four languages, they must be reached through the same create/run shape with the same result fields so callers can switch language by a single argument. Confidence: 0.7
- Prefers reusable functionality packaged as a standalone, consumable npm library (with its own public API surface) rather than living only inside the app/demo that first needed it. Confidence: 0.45
- Wants published packages to be self-contained: bundles the binary/runtime assets into the npm package itself so that consumers need no separate hosting, CDN, or server. Confidence: 0.7
- Prefers the most permissive license available, provided it is verified compatible with every dependency and redistributed third-party component — avoiding copyleft obligations on users and on the programs they build. Confidence: 0.8
- Wants upstream-hosted resources kept as a committed local mirror as insurance against the upstream host disappearing, rather than relying solely on remote availability. Confidence: 0.7
- Given a licensing obligation that can be closed either by deleting the offending files or by satisfying it, prefers keeping the files and meeting the obligation (shipping the corresponding source, license text, and a written offer) rather than removing them — even for large, unused artifacts. Confidence: 0.4
- Wants published libraries usable in classic, non-module contexts: asks for a minified IIFE bundle loadable via `importScripts()` from a plain (non-module) worker, so consumers need neither a bundler nor an import map. Confidence: 0.45
- Wants copyleft/non-permissive dependencies isolated into a separate, dynamically-loaded project/distribution (e.g. loaded at runtime via a configurable base URL) rather than bundled into the main permissively-licensed package — and asks whether that split is actually sufficient for compliance rather than assuming it is. Confidence: 0.5
- Prefers the simplest correct form over an exhaustive or technically-precise one: for licensing, asked to "keep it simple, no special notices" — a plain single license (`MIT`) rather than the multi-term SPDX expression describing every bundled dependency, and a minimal notice header rather than an elaborate one. Confidence: 0.5
